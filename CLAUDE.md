# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

This is **LLM Vault** - a Chrome extension (Manifest V3) that exports Claude Project conversations or single conversations, and now ChatGPT Project conversations, as structured `.zip` files containing Markdown. It supports both claude.ai and chatgpt.com. ChatGPT support currently covers project-scoped export only (single project and multi-project batch); standalone (non-project) ChatGPT conversations are not yet exportable — see ChatGPT Export below.

## Architecture

- `extension/manifest.json` - Manifest V3 config (permissions: `downloads`, `activeTab`, `cookies`, `sidePanel`, `tabs`, `scripting`; host permissions: `https://claude.ai/*`, `https://chatgpt.com/*`). The `scripting` permission backs `sendMessageWithRecovery` (see `sidepanel.js` below) — it lets the extension re-inject a missing content script on demand rather than requiring the user to manually refresh the tab.
- `extension/background.js` - Minimal service worker; its only job is calling `chrome.sidePanel.setPanelBehavior({openPanelOnActionClick: true})` so clicking the toolbar icon opens the side panel.
- `extension/sidepanel.html` / `extension/sidepanel.js` - Side panel UI (persistent, docked to the browser window — replaces the old popup): a permanent home section (title, value-prop description, "Open Claude" / "Open ChatGPT" buttons that navigate the active tab via `chrome.tabs.update`, highlighting whichever site the active tab is currently on) sits above a visual separator, then a permanent "Project" / "Conversation" navigation block (visible whenever the active tab is on claude.ai or chatgpt.com, navigating to each provider's projects listing — `claude.ai/cowork/projects` / `chatgpt.com/projects` — or conversation history — `claude.ai/chats` / `chatgpt.com/`, the closest ChatGPT equivalent since it has no dedicated history URL — and highlighting the matching button when already on that page), then the contextual panel, which detects context (project vs conversation vs neither) from the active tab's URL, re-detects on tab switch/navigation (`chrome.tabs.onActivated`/`onUpdated`, since the panel doesn't reload like a popup did), orchestrates the export pipeline, shows progress/status. Each of the three selection-mode flows (Claude projects, Claude recents, GPT projects) also shows a "Cancel" button alongside its "Confirm Selection" button, letting the user exit selection mode without confirming or navigating away. At the 5 real entry-point call sites (`enterSelectionMode`, `enterRecentsSelectionMode`, `runExport`'s two branches, `startGptSelection`, plus `gptScrapeProject` in `gptExport.js`), messages to the content script go through `sendMessageWithRecovery(tabId, message, contentScriptFile)`: on a `chrome.tabs.sendMessage` failure (typically because the extension was reloaded while the tab was already open — Manifest V3 only auto-injects content scripts into tabs that load *after* the extension becomes active), it injects the missing content script via `chrome.scripting.executeScript` and retries once, so the common case recovers without a manual page refresh. Call sites inside an already-running batch/export loop are deliberately left on plain `chrome.tabs.sendMessage`, since the content script there was just injected by the navigation immediately preceding the call.
- `extension/lib/orgId.js` - Project/conversation ID extraction from URLs; organization ID lookup via `chrome.cookies.get` on the `lastActiveOrg` cookie.
- `extension/lib/api.js` - Fetches the conversations list and individual conversations from claude.ai's internal API, with batching (5 at a time) and exponential-backoff retry on rate limiting (429).
- `extension/lib/markdown.js` - Converts conversation JSON to Markdown; builds the project index; sanitizes filenames.
- `extension/lib/zipBuilder.js` - Builds the in-memory folder tree and generates the zip Blob via vendored JSZip.
- `extension/lib/jszip.min.js` - Vendored JSZip (no CDN — Manifest V3 CSP disallows remote code).
- `extension/content.js` - Content script injected on `claude.ai/project/*` and `claude.ai/chat/*`; scrapes the project's Memory/Instructions text (project pages) and scrapes artifact/content filenames (chat pages) from the DOM on request (no REST API exposes this data). Also injected on `claude.ai/projects` (exact path, no wildcard) to power multi-project selection — see Multi-Project Batch Export below.
- `extension/content-gpt.js` - Content script injected on `https://chatgpt.com/*`; the ChatGPT counterpart to `content.js`, entirely independent of it (no shared code). DOM-scrapes project instructions and the project's conversation list, calls ChatGPT's internal `/backend-api` to fetch conversation content and files, and powers projects-list multi-selection. See ChatGPT Export below.
- `extension/lib/gptDetect.js` - ChatGPT host/URL detection (`isGptHost`, `gptDetectContext`) — the ChatGPT counterpart to `orgId.js`'s ID extraction.
- `extension/lib/gptMarkdown.js` - Converts scraped ChatGPT project/conversation data to Markdown; writes each turn's already-Markdown text as-is (no HTML→Markdown conversion needed — see ChatGPT Export below). Builds the project index and instructions files; sanitizes filenames.
- `extension/lib/gptExport.js` - ChatGPT scrape-and-build pipeline (`gptScrapeProject`, `gptBuildProjectInto`) — the ChatGPT counterpart to `api.js`/`zipBuilder.js`'s combined responsibilities.

## Key Technical Details

### ID Extraction
- Project ID: parsed from the active tab's URL, pattern `/project/[uuid]`.
- Conversation ID: parsed from the active tab's URL, pattern `/chat/[uuid]`.
- Organization ID: read from the `lastActiveOrg` cookie via `chrome.cookies.get({url: 'https://claude.ai', name: 'lastActiveOrg'})`. Unlike the old console-script approach, the side panel has no access to the page's `localStorage`/`sessionStorage`/JS globals, so there is no fallback chain beyond the cookie — if it's missing, export fails with an explicit error asking the user to confirm they're logged in.

### API Flow
1. **Conversations List** (project mode only): `GET /api/organizations/[org]/projects/[project]/conversations_v2`
2. **Individual Conversations**: `GET /api/organizations/[org]/chat_conversations/[conv]?tree=True&rendering_mode=messages&render_all_tools=true`
3. All fetches use `credentials: 'include'` to leverage the existing claude.ai browser session.

### Output Structure
Every export is a single `.zip` download (built with vendored JSZip, never written to disk as loose files):
- Project export: `index.md` at the root, plus `memory.md`/`instructions.md` (only if found — see Project Metadata Scraping below), plus `fichiers/` (populated with the project's image knowledge files — see Project Knowledge Files Capture below), plus a `Conversations/` folder holding one subfolder per conversation (`Conversations/<title>_<uuid8>/`, keeping the root itself uncluttered when a project has many conversations), each containing `conversation.md`, `artefacts/` (populated the same way as single-conversation export), `contenu/` (populated the same way as single-conversation export, including image attachments — see Conversation Artifact & Content Capture below for how project export captures these for every conversation). `index.md`'s own conversation links point into `Conversations/` accordingly.
- Single conversation export: one folder with `conversation.md`, `artefacts/` (populated with unzipped Claude-generated artifacts if any were captured, otherwise empty), `contenu/` (populated with fetched image attachments if any were found, otherwise empty). No index, no memory/instructions/fichiers (project-only concepts).

`fichiers/` (project knowledge files) is populated with the project's image knowledge files — see Project Knowledge Files Capture below. Non-image knowledge files (e.g. `.docx`, `.pdf`) are not yet covered.

### Project Metadata Scraping (Memory & Instructions)
Claude's Memory and Instructions text for a project is not exposed by any REST API the extension uses — it only exists rendered in the project page's DOM. `extension/content.js` is injected on `claude.ai/project/*` pages and, on request (`chrome.runtime.onMessage` with `{type: 'GET_PROJECT_METADATA'}`), scans for `<h3>` elements matching the exact label text `"Mémoire"`/`"Instructions"` (French UI only — no i18n support), then walks up to 5 ancestor levels looking for a sibling `<p>` with the section's text. During a project export, `sidepanel.js` messages the active tab's content script and passes the result into `buildProjectZip`; if the content script isn't present/responsive (page not loaded, wrong page, or a UI change broke the selectors), the export proceeds without `memory.md`/`instructions.md` rather than failing — this is enrichment, not a required part of a successful export.

### Project Knowledge Files Capture
The project's "Fichiers" section (project-level knowledge files, distinct from a conversation's own attachments) lives directly on the project page, structured identically to a conversation's "Contenu" section: a `<h3>Fichiers</h3>` heading followed by a thumbnail grid. `getProjectMetadata()` in `extension/content.js` scrapes this section's `<img alt src>` thumbnails the same way `scrapeImageContentFiles()` already does for conversation content files, returning `{filename, url}` pairs as a `files` field alongside `memory`/`instructions` — reusing the existing `GET_PROJECT_METADATA` message rather than adding a new one, since it's already sent once per project export and already degrades gracefully if the content script is unreachable. Only image files are captured this way; non-image files in this section (e.g. `.docx`) render with no `<img>` and are silently skipped — their download mechanism is unconfirmed and not yet implemented. `extension/lib/zipBuilder.js`'s `buildProjectZip` fetches every scraped file into `fichiers/` via the same `fetchFilesInto()` helper already shared by `artefacts/`/`contenu/`, falling back to an empty `.gitkeep` placeholder if the section was empty/absent or every fetch failed.

### Conversation Artifact & Content Capture
Neither a conversation's Claude-generated artifacts nor its individually-attached files are exposed by a REST API endpoint that returns their content directly — both are downloaded via `GET /api/organizations/{org}/conversations/{conv}/wiggle/download-file?path=<url-encoded /mnt/user-data/... path>` (confirmed via live Network captures — a real navigation with `Content-Disposition: attachment`, not a client-side-generated Blob, so there is nothing to intercept).

The real on-disk path for each file is not exposed by any dedicated field, but it turns out to already be present as plain text inside the conversation JSON that `sidepanel.js` fetches for every export anyway (via `fetchConversation`) — in `chat_messages[].files[].path` for uploads, and inside `tool_use`/`tool_result` content (bash commands, command output) for files Claude writes to `/mnt/user-data/outputs/`. `extractFilePaths()` in `extension/lib/api.js` regex-scans the whole `JSON.stringify()`-ed response for `/mnt/user-data/(uploads|outputs)/...` occurrences — restricting the filename portion to characters plausible in a real filename (word chars, spaces, dots, hyphens, parens) rather than reading until the next quote, since some matches sit inside multi-line bash command strings where a naive "up to the next quote" read would swallow the rest of the command as part of the "path". This replaced an earlier DOM-scraping approach that guessed each artifact's on-disk filename from its card's "humanized" title (e.g. "Keensight slide library v2" → guessed `keensight_slide_library_v2.zip`) — confirmed via a live test to guess wrong roughly half the time (a hyphenated real filename, and one with different casing/underscores than its title, both silently dropped).

`sidepanel.js` builds a `download-file?path=...` URL for every extracted path — outputs paths become `artefacts/` entries, uploads paths become `contenu/` entries — plus image attachments, which still need one DOM scrape: `extension/content.js`'s `getConversationArtifacts()` opens the Files sidebar (`[aria-label="Fichiers"]`, skipped if `aria-pressed="true"` already — clicking an already-open toggle would close it) to reach the "Contenu" section (distinct from the project-level "Contenu du projet") and scrape `<img alt src>` thumbnails for their `/preview` URLs, since those aren't derivable from a `/mnt/user-data` path. `extension/lib/zipBuilder.js`'s `fetchFilesInto()` helper then fetches every URL in a list (`credentials: 'include'`) directly into its target folder, skipping individual failures without aborting the export — a folder falls back to an empty `.gitkeep` placeholder only if every fetch in it failed.

**Project export** (single-project and multi-project batch alike) now captures the same data for every conversation in the project, in two phases: a JSON-only phase (`buildArtifactsDataFromConversationJson`, shared with single-conversation export) that runs immediately after the existing batched `fetchAllConversations` call — no navigation needed, since artifact/uploaded-file paths come from each conversation's own JSON — followed by a sequential per-conversation navigation phase (`captureProjectConversationImages`) that visits each conversation's page in the active tab (status: `"Capturing images N/Total: <name>..."`) purely to scrape image content files' `/preview` URLs, the one piece of data that requires the DOM. A conversation whose navigation fails keeps its JSON-derived data; only its images are skipped. `buildProjectZip` takes an optional `artifactsDataByUuid` map (keyed by each conversation's `metadata.uuid`) to thread this per-conversation data through — omitting it (as no call site now does) falls back to the original always-empty behavior.

### Multi-Project Batch Export
On `claude.ai/projects`, `extension/content.js` gains a "selection mode": on `{type: 'START_SELECTION_MODE'}`, it attaches a capture-phase click listener to the `<ul aria-label="Projets">` project list that intercepts clicks (`preventDefault`/`stopPropagation`, blocking normal navigation) and toggles a red CSS outline plus an in-memory `Set` of selected UUIDs. `{type: 'GET_SELECTED_PROJECTS'}` returns the current selection as `{uuid, name}` pairs; `{type: 'STOP_SELECTION_MODE'}` tears the listener/borders down. `sidepanel.js` shows a "Select Projects" button on the listing page, polls the selection every 500ms to keep a live "Confirm Selection (N)" count, then on confirm drives a sequential batch: for each selected project it navigates the SAME active tab (`chrome.tabs.update`), waits for the freshly-injected content script to respond to `{type: 'PING'}` (checked against the content script's own `window.location.pathname` in the response, not just any `{pong: true}` — a stale content script on the previous page can otherwise still answer PING for a brief window after `chrome.tabs.update()` resolves, since that call resolves once navigation is *initiated*, not once it *completes*), then runs the same fetch/scrape pipeline as single-project export against one shared `JSZip` instance (via `buildProjectZip(zip, folderPath, ...)` — refactored to accept a caller-supplied zip/folder rather than always creating and generating its own, so multiple projects can be nested into one combined zip). Each project's subfolder is `<sanitizeFilename(project.name)>_<uuid's first 8 chars>` — the uuid suffix (same convention as a conversation folder's own `<title>_<uuid8>`) guards against two same-named projects silently overwriting each other in the combined zip, which a name-only folder can't. A `batchInProgress` flag (checked by the same `detectContext()` early-return guard used for `selectionMode`) plus disabling `#export-btn` for the batch's duration prevent the pre-existing `chrome.tabs.onUpdated`-triggered `detectContext()` calls (fired by the batch's own navigation) from re-enabling single-project export against the tab the batch is actively driving. A project that fails at any step (navigation timeout, empty conversation list, fetch failure) is recorded and skipped — the batch continues with the rest, and no zip is generated at all if every project fails. One combined `.zip` (`claude_projects_batch_<count>.zip`) downloads once, after the loop.

### Recents Page Multi-Conversation Selection
On `claude.ai/recents`, `extension/content.js` implements a fully independent selection mechanism (distinct from both the projects-list selection and Claude's native table-based row-selection UI, which is for bulk-delete, not export). On `{type: 'START_RECENTS_SELECTION_MODE'}`, it attaches a capture-phase click listener to the `<table data-cds="Table">` recents table that intercepts clicks on rows (`tbody tr[data-hoverable]`) and toggles a red CSS outline plus an in-memory `Set` of selected conversation UUIDs. `{type: 'GET_SELECTED_RECENTS_CONVERSATIONS'}` returns the current selection as `{uuid, name}` pairs; `{type: 'STOP_RECENTS_SELECTION_MODE'}` tears the listener/borders down. A "Select All" shortcut is available via `{type: 'SELECT_ALL_RECENTS_CONVERSATIONS'}`, which auto-scrolls the page to the document bottom repeatedly, polling `waitForRowCountToStabilize()` to detect when lazy-loading has finished — it performs 3 consecutive stable row-count checks at 500ms intervals (1.5 seconds of no new rows) or times out after 30 seconds total, whichever comes first, then selects every row found and returns the total count. `sidepanel.js` shows a "Select Recents" button on the recents page that enters this selection mode and displays a live "Confirm Selection (N)" count, polled every 500ms. It also offers a "Select All" button for the auto-scroll bulk-select. On confirm, `startRecentsExport()` reuses the same fetch/scrape pipeline as project export (`fetchAllConversations`, `buildArtifactsDataByUuid`, `captureProjectConversationImages`) for complete data capture — text, Claude-generated artifacts, user-uploaded files via JSON-parsed paths, and image content files via per-conversation navigation. The result is written via `buildConversationsSelectionZip()` to a single `.zip` containing `index.md` at the root plus one folder per conversation (`<title>_<uuid8>/`), each with `conversation.md`, `artefacts/`, and `contenu/` — no `memory.md`/`instructions.md`/`fichiers/` (project-only concepts), and no nested project folders. The zip downloads as `claude_conversations_selection_<count>.zip` once all conversations are processed. A `batchInProgress` flag and disabled export button prevent interference from tab navigation during the export, using the same `detectContext()` guarding as project batch export.

### Rate Limiting & Batching
- Conversations fetched in batches of 5, with a 500-750ms delay between batches (750ms above 50 conversations).
- Individual conversation fetch retries up to 3 times on failure, with exponential backoff starting at 1000ms (capped at 10000ms) on HTTP 429.
- Partial failures are tolerated: if some conversations fail to fetch, the export still completes with the successful ones, and the status message reports how many failed.

## ChatGPT Export

ChatGPT support is a fully isolated pipeline living in its own files (`extension/lib/gptDetect.js`, `extension/lib/gptMarkdown.js`, `extension/lib/gptExport.js`, `extension/content-gpt.js`, plus the `gpt*`-prefixed functions added to `extension/sidepanel.js`) — none of the existing Claude modules were modified beyond `sidepanel.js`'s top-level routing and the one shared helper noted below. The project's conversation list and each conversation's content/files are intentionally scraped/visited via the real DOM, not resolved invisibly through an API: multi-project selection on `/projects` has no API alternative at all (ChatGPT exposes no endpoint listing all of a user's projects), and the project page's own "Chats" tab and each conversation page are deliberately navigated to and highlighted/visited one by one, so the export is something a user can watch happen rather than a silent background fetch. Only project metadata (name/instructions) is fetched from the gizmos API rather than DOM-scraped — see below — because that enrichment step was never the source of any navigation flakiness; conversation content and file downloads are fetched from ChatGPT's internal `/backend-api` once the tab has navigated to each conversation's own page.

### URL Detection
`gptDetectContext()` in `extension/lib/gptDetect.js` classifies the active tab's `chatgpt.com` URL into one of three kinds (returns `{kind: null}` for anything else, including non-`chatgpt.com` hosts):
- **Projects list**: exact path `/projects` → `{kind: 'projects'}`.
- **Project page**: `/g/g-p-<hex-id>(-<slug>)?/project` → `{kind: 'project', projectId}`.
- **Conversation page**: `/g/g-p-<hex-id>(-<slug>)?/c/<uuid>` → `{kind: 'conversation', projectId, convId}` — the slug is optional here too (ChatGPT's project page dropped it from conversation links circa Oct 2026, now plain `/g/g-p-<id>/c/<convId>`; both shapes are still accepted since a slugged link can still appear elsewhere).

`isGptHost(url)` checks `hostname === 'chatgpt.com'`. `extension/sidepanel.js`'s `detectContext()` calls `isGptHost()` first and, if true, delegates entirely to `detectGptContext()` — a separate branch from the Claude URL-pattern checks (`getProjectIdFromUrl`/`getConversationIdFromUrl`/etc.), so Claude and ChatGPT routing never intermix. Only the projects-list and project-page kinds currently drive UI (a "Select GPT Projects" button and an "Export GPT Project" button respectively); the conversation kind and anything unrecognized fall through to a generic "navigate to a project" message — standalone conversation export is not implemented.

### Project Metadata & Conversation List (Phase 1 & 2)

A ChatGPT "Project" is a "gizmo" on the backend, identified by a `g-p-<hex>` id. Every project's id is resolved up front via `gptGetAllProjectIds()` — see Multi-Project Selection below — so by the time a project's own page is navigated to, its id is already known, not discovered from that page.

- **Metadata**: `gptGetProjectMetadata()` in `content-gpt.js` calls `GET /backend-api/gizmos/<projectId>?include_file_limits=true` (via `gptApiGet()`, same helper used for conversation content — see below), reading `{name: resp.gizmo.display.name, instructions: resp.gizmo.instructions}`, plus `sources` (the project's "Sources" tab files — see Project Sources below) from the same response's top-level `files` array. Falls back to the page's own `<h1>`/`button[name="project-title"]` text (no instructions, no sources) if the project id can't be determined from the URL or the request fails — this is enrichment, not a required part of a successful export. This one piece of project-scoped data is deliberately still fetched via the API rather than DOM-scraped: unlike the conversation list below, it was never the source of any navigation-timing flakiness, so there's no reason to trade its reliability for visibility.
- **Conversation list**: `gptGetProjectConversations()` scrapes the project page's "Chats" tab for `<a href*="/c/">` links matching `/\/g\/g-p-[a-f0-9]+(?:-[^/]*)?\/c\/[a-f0-9-]+/` (confirmed live: `/g/g-p-<id>/c/<convId>`, no slug on this page specifically), de-duplicating by conversation UUID and reading each link's title from its `.text-sm.font-medium` child (falling back to the UUID). This is deliberate DOM-scraping, not an API call: the project is meant to actually render and its conversations be visited one by one, matching what a user watching the tab sees. `gptWaitForListToStabilize()` polls the link count (3 consecutive stable checks 500ms apart, or a 15s timeout) to handle the list still rendering a moment after navigation, and `gptHighlightConversationRows()` outlines every found link (same gold/amber style as selection mode) so the match is visually confirmable before `gptScrapeProject()` starts visiting them.
- **The project id, once already on its page**: `gptGetProjectIdFromLocation()` extracts `g-p-<hex>` from `window.location.pathname` (mirroring `gptDetectContext`'s pattern) — used by `gptGetProjectMetadata()` above once the content script is running on the project page (which it always is for this call, since navigation there is now a plain URL navigation to a known id — see Multi-Project Selection below).

### Project Sources

A project's "Sources" tab files are downloaded without ever scraping that tab's own DOM, language-independently, the same way the "Start new chat"/project-navigation button issue (see Multi-Project Selection below) was solved by going straight to an API: the response from `GET /backend-api/gizmos/<projectId>?include_file_limits=true` — already fetched by `gptGetProjectMetadata()` for name/instructions — has a top-level `files` array (not nested under `gizmo`) of `{file_id, name, ...}` for every Sources-tab file, read into `project.sources` as `{fileId, name}` pairs at essentially no extra cost.

`gptScrapeProject()` in `extension/lib/gptExport.js` downloads them right after fetching metadata, while still on the project page: sends `{type: 'DOWNLOAD_GPT_PROJECT_SOURCES', sources: project.sources}`, handled by `gptDownloadProjectSources(projectId, sources)` in `content-gpt.js` (the `projectId` comes from `gptGetProjectIdFromLocation()` on the content-script side, not the message, since the tab is already on that project's page). Each source is downloaded via the same `gptDownloadFile()` helper used for conversation attachments, with `download_intent=true&gizmo_id=<projectId>` appended to the `files/download/<fileId>` request — confirmed via a live test against a real project's two Sources-tab files that this is what a project-level source's download link actually needs (a conversation attachment's download works the same way without those params; this is the one place they're needed). Results land in `project.sourceFiles` (`[{filename, bytesBase64}]`); a project with an empty `sources` list skips the whole step with no extra request. A project with no Sources tab at all behaves identically — `gizmo` files simply come back empty.

### Conversation Content & Files via `/backend-api` (Phase 3)
Rather than scraping the rendered thread DOM, conversation content and files are fetched directly from ChatGPT's internal `/backend-api`, called from `content-gpt.js` running in the page (so browser session cookies apply, no separate auth needed):

- **Session token**: `gptGetSessionToken()` fetches `GET /api/auth/session` (`credentials: 'include'`) and caches its `accessToken` in memory (`gptCachedToken`) for the life of the content script. Throws if the response has no token (e.g. logged out).
- **API requests**: `gptApiGet(path, token)` calls `GET /backend-api/<path>`, with headers built by `gptApiHeaders()` — `Authorization: Bearer <token>`, plus `Oai-Device-Id` (a `crypto.randomUUID()` generated once per content-script instance and reused) and `Oai-Language: en-US`.
- **Conversation JSON**: `gptGetConversationViaApi(convId)` calls `gptApiGet('conversation/<convId>', token)`, which returns the full conversation as a `mapping` — a tree of message nodes keyed by node ID, each with a `parent` and `children` list (ChatGPT's native storage format, not something rendered 1:1 in the DOM).
- **Turn extraction**: `gptMappingToTurns(convo, fileMap)` in `content-gpt.js` finds the root node (the one with `parent == null`) and walks the tree breadth-first, skipping `system`/`tool` roles and any non-text assistant content (e.g. tool-call nodes). Each surviving node's `content.parts` are joined into a single Markdown string per turn: plain string parts are used as-is; `image_asset_pointer` parts are resolved through `fileMap` (built from files already downloaded in the same pass — see below) into a Markdown image link, or rendered as a `[image]` placeholder if not in the map; `metadata.attachments` become an appended `📎 [name](path)` link. Citation markup (`【...】`) is stripped via `gptStripCitations()`. The result is a flat list of `{role: 'user'|'assistant', markdown}` turns — already Markdown, not HTML, so no HTML→Markdown conversion step exists or is needed.
- **File references & downloads**: `gptExtractFileReferences(convo)` scans the same `mapping` for three kinds of file pointers — `image_asset_pointer` parts (`file-service://` or `sediment://` URIs), `metadata.attachments`, and `metadata.citations` — de-duplicating by file ID. For each reference, `gptDownloadFile(fileId, fallbackName, token, usedNames)` calls `GET /backend-api/files/download/<fileId>` to obtain a `download_url`, fetches that URL for the raw bytes, infers a file extension from the response's `Content-Type` when the filename doesn't already have one (`GPT_MIME_TO_EXT` table), de-duplicates the filename against others already downloaded in the same conversation (`gptDeduplicateFilename`), and returns `{filename, bytesBase64}` — the bytes base64-encoded (`gptBytesToBase64`) so they can cross the content-script/background-page message boundary as plain JSON. All file types are downloaded this way, not just images. A 300ms delay is inserted between downloads; a failed download is skipped (logged nowhere, simply omitted) without aborting the rest of the conversation.
- **Message type**: `sidepanel.js`/`gptExport.js` requests this whole pipeline per conversation via `chrome.tabs.sendMessage(tabId, {type: 'GET_GPT_CONVERSATION_VIA_API', convId})`, handled in `content-gpt.js`'s `onMessage` listener, which responds with `{title, createTime, turns, files}` (or `{error: true}` on failure, letting the caller fall back to empty turns/files for that conversation rather than aborting the whole export). Although this is a same-origin `/backend-api` fetch keyed purely by `convId` — it reads nothing from a specific conversation page's DOM, so it doesn't technically require the tab to be on that conversation's page — `gptScrapeProject()` in `extension/lib/gptExport.js` navigates the tab to each conversation's URL before sending it anyway: the user wants to see each conversation actually open and be visited one by one, not have everything resolved invisibly while the tab stays on the project page. A conversation whose page doesn't load in time (`waitForContentScriptReady`, 15s) keeps its scraped title/URL but gets empty turns/files rather than aborting the whole project.
- **Title**: `gptScrapeProject()` prefers this response's own `title` over the one `gptScrapeConversationList()` scraped from the project page's `.text-sm.font-medium` link text — that DOM scrape falls back to the raw `convId` when its selector doesn't match a given row (observed live on a real project: one conversation's title element wasn't where expected, producing a zip folder literally named `<uuid>_<uuid8>`), and the API's own `title` field is always the real one. `{...conv, title: apiTitle || conv.title, ...}` only overrides when the API title is non-empty, so a conversation whose page failed to load (no API call made at all) still keeps whatever the DOM scrape found.

### Output Structure
Every ChatGPT export is a single `.zip` download, built the same vendored-JSZip way as Claude exports:
- **Single project**: `gpt_project_<sanitized-name>.zip` containing `index.md` at the root (project name heading, a `## Conversations` list linking into `Conversations/` for each conversation's `conversation.md`, and a `## Sources` list linking into `fichiers/` **only if the project had any Sources-tab files** — see Project Sources above), `instructions.md` **only if the scraped instructions were non-empty** (unlike Claude's Memory/Instructions files, which are separately optional), a `fichiers/` folder (only created when `project.sourceFiles` is non-empty — no `.gitkeep` placeholder for an empty/absent Sources tab, unlike every other fallback-to-`.gitkeep` folder in this export, since there's nothing project-level to signal besides the files themselves) holding every downloaded source file — same folder name as Claude's project knowledge files, though this one covers all file types rather than only images — and a `Conversations/` folder (matching Claude's project-export structure) holding one subfolder per conversation (`gptConvFolderName()`: `Conversations/<sanitized-title>_<uuid8>/`), each containing `conversation.md` (built by `gptTurnsToMarkdown()` from the API-derived `{role, markdown}` turns) and a `contenu-gpt/` folder holding every file downloaded via `/backend-api/files/download/<fileId>` for that conversation (`gptBuildConversationFolder()` decodes each file's base64 bytes back to binary with `gptBase64ToBytes()`), falling back to an empty `.gitkeep` if the conversation had no files or every download failed — same fallback convention as Claude's `contenu`/`artefacts`/`fichiers`.
- **Multi-project batch**: `gpt_projects_batch_<succeeded-count>.zip`, one JSZip subfolder per project (named from the scraped project name, via `gptBuildProjectInto(zip, folderName, ...)`), same per-project contents as the single-project case, combined into one zip the same way Claude's multi-project batch nests into one `JSZip` instance.
- There is **no** `artefacts/` folder or `memory.md` in ChatGPT output — those are Claude-specific concepts (Claude-generated sandbox artifacts and a Memory feature) with no ChatGPT equivalent scraped yet. `contenu-gpt/` folds together what Claude keeps separate as `contenu/` (uploads) vs `artefacts/` (assistant-generated) — ChatGPT's API doesn't currently distinguish the two the way Claude's does.

### Multi-Project Selection (index-based selection, ids resolved via the sidebar endpoint)

ChatGPT's projects-list rows (`[data-project-row]`, each inside a `[data-project-row-wrapper]` that also holds that project's own inline-expanded conversation preview — no `role="grid"`/`role="row"` ARIA markup; ChatGPT dropped that circa Oct 2026) expose no `g-p-<hex>` id or href anywhere in the DOM, and clicking the row itself does nothing but toggle that inline preview in place (confirmed live — no URL change). `content-gpt.js` therefore keys selection by **row index**: `gptHandleSelectionClick()` (attached capture-phase on `document.body`, `{type: 'START_GPT_SELECTION_MODE'}`) finds the clicked row's position via `gptFindProjectRows().indexOf(row)` and toggles it in a `Map<index, name>` — the **name is captured at click time** (`gptRowName()`, reading the row's `span.truncate`) specifically so a later list reorder/filter can't change what name is later reported for that index. `{type: 'GET_GPT_SELECTED_PROJECTS'}` (cheap, synchronous — reads straight from that in-memory `Map`) returns `[{index, name}]`, polled every 500ms by `startGptSelection()` in `sidepanel.js` purely to keep the "Confirm Selection (N)" count live; `{type: 'STOP_GPT_SELECTION_MODE'}` clears the `Map` and CSS outline.

**Resolving ids**: confirming the selection (`confirmGptSelection()`) sends `{type: 'GET_GPT_SELECTED_PROJECTS_WITH_IDS'}` instead — a separate, async message from the plain one above, since resolving ids means a network call and doing that on every 500ms poll tick would be wasteful. `gptGetSelectedProjectsWithIds()` calls `gptGetAllProjectIds()`, which fetches `GET /backend-api/gizmos/snorlax/sidebar?conversations_per_gizmo=0&limit=50&owned_only=true` — the same internal endpoint ChatGPT's own sidebar uses to render the user's project list — and builds a `name → id` map from its `items[].gizmo.{gizmo.,}id`/`.display.name` (the per-item shape has been observed both with and without an extra nesting level, so both are unwrapped defensively). Each selected `{index, name}` gets `id: idByName.get(name) || null` attached; a `null` id (sidebar fetch failed, or a name with no match) makes that project fail outright in the batch rather than guessing.

This replaced an entire earlier mechanism that tried to discover a project's id by clicking something on its `/projects` row and reading the id back out of the resulting URL — confirmed live, across several attempted fixes, to be unreliable in multiple independent ways: the click itself was intermittent (a manually dispatched `pointerdown`/`mousedown`/`pointerup`/`mouseup`/`click` event sequence, meant to be "more robust" than a plain `.click()`, instead sometimes triggered no navigation at all), and even when the click did land, the resulting React-Router-only URL change sometimes left the project page's own component unmounted (URL correct, page blank). Having every project's real id up front removes the click from the equation entirely: `gptNavigateToProject()` in `sidepanel.js` is now a plain `chrome.tabs.update(tabId, {url: 'https://chatgpt.com/g/<id>/project'})` — an ordinary browser navigation, not a synthetic interaction with anything on the `/projects` page.

`gptNavigateToProject()` in `sidepanel.js` navigates and then waits via the usual `waitForContentScriptReady()` (20s timeout, checked against the project page's own `/g/<id>/project` path) — a real `chrome.tabs.update` to a URL the tab wasn't already at always triggers a full page load, so there is no React-Router-route-change-without-mounting failure mode to work around here (that failure mode was specific to the earlier click-based approach, where the URL change came from client-side routing rather than an actual navigation). `gptScrapeProject()` in `extension/lib/gptExport.js` is handed that confirmed-ready `projectUrl` and does not navigate again.

`gptScrapeProject()` reads the project id straight out of the current URL (`gptGetProjectIdFromLocation()`) for the one metadata call that still needs it (`GET_GPT_PROJECT_METADATA`) — and, as a **guardrail**, compares the project name read from that metadata against the name captured at selection time; if they disagree, the project is skipped and recorded as `"<expectedName> (mismatch: got \"<apiName>\")"` rather than exporting the wrong project's data under the selected name. A project that fails at any step (navigation timeout, empty conversation list, name mismatch, scrape error) is recorded and skipped; the batch continues with the rest, and (mirroring Claude's batch) no zip is generated if every project fails. Each project's subfolder in the combined zip is `<gptSanitizeFilename(name)>_<id's last 8 chars>` — mirroring Claude's batch's own `<name>_<uuid8>` folder naming (the suffix guards against two same-named projects overwriting each other); the *last* 8 characters of the `g-p-<hex>` id are used rather than the first, since every id shares the same `g-p-` prefix and the hex part only actually varies toward the end of what a `slice(0, 8)` would otherwise grab.

### Shared Helper Change: `waitForContentScriptReady`
`waitForContentScriptReady()` in `extension/sidepanel.js` is shared, unmodified in its role, between Claude and ChatGPT flows, but its pathname check was relaxed from exact equality to substring (`response.pathname.includes(expectedPathname)`) to accommodate ChatGPT's URL shape — a conversation path like `/g/g-p-<id>-<slug>/c/<uuid>` needs to match on the `/c/<uuid>` suffix without the caller having to reconstruct the full path (including the arbitrary `-<slug>` segment) up front. This is a behavior-preserving generalization for Claude's own exact-path use sites (an `includes` check still matches an exact equal string).

### Known Limitations
- All file types referenced in a ChatGPT conversation (images, attachments, citation-linked files) are now downloaded via `/backend-api/files/download/<fileId>` into `contenu-gpt/` — this is no longer limited to images.
- Long-thread virtualization is no longer a concern: `conversation/<convId>` returns the full `mapping` tree for the whole thread in one response, so there is nothing to scroll/de-virtualize or spot-check against turn counts.
- Standalone (non-project) ChatGPT conversations are not exportable — `gptDetectContext`'s `'conversation'` kind is recognized but has no export UI/pipeline wired to it yet.

## Development Guidelines

### Code Standards
- Pure vanilla JavaScript - no frameworks, no bundler, no build step.
- Manifest V3 - all scripts loaded via `<script>` tags in `sidepanel.html`, no ES modules, no dynamic `import()`.
- The only external dependency is the vendored `jszip.min.js` - do not add a CDN reference (blocked by MV3 CSP).

### Testing Approach
No automated test suite. Manual verification against a live claude.ai session, covering:
1. Empty project (0 conversations).
2. Small project (1-20 conversations).
3. Larger project (50+ conversations) - verify batching/delay behavior.
4. Single conversation export outside a project.
5. Logged-out / auth failure state.
6. Side panel opened on an unrelated claude.ai page or a different site - should show the "navigate to a project/conversation" message, no button.
7. Side panel context updates correctly when switching tabs or navigating within the same tab, without needing to close/reopen the panel.

### Testing New Changes
1. Open `chrome://extensions`, enable Developer mode.
2. Click "Load unpacked" (first time) or the refresh icon on the extension card (after edits) and select/reload the `extension/` folder.
3. Navigate to a Claude project or conversation page and use the side panel (click the toolbar icon to open it if not already open).
4. Inspect the panel's console via right-click inside the panel → Inspect for `console.log`/error output.

## Security Considerations

- Client-side only - no data sent anywhere except claude.ai's own API.
- Uses the browser's existing claude.ai session (cookies) - no credential storage by the extension.
- No external dependencies loaded at runtime - JSZip is vendored, not fetched from a CDN (MV3 CSP requirement).

## Distribution

This extension is developer-mode only (unpacked) - it is not published to the Chrome Web Store. There is no `key` field in the manifest and no store-review-oriented permission minimization beyond what's functionally required.
